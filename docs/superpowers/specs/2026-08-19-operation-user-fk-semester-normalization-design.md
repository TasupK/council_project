# OperationDB 사용자 FK 및 학기기준 정규화 설계

## 1. 목적

이번 작업은 OperationDB의 사용자 참조 컬럼을 UserDB의 `사용자.Google이메일` 기준으로 통일하고, 비어 있는 `학기기준` 테이블을 실제 참조 가능한 기준 테이블로 복구하는 것을 목표로 한다.

Accounting v2 및 프론트엔드 전수 정합화는 이번 범위에 포함하지 않는다.

## 2. 현재 문제

### 2.1 학기기준 FK 단절

`학기기준` 시트는 헤더만 존재하고 실제 기준 데이터가 없다. 반면 `회비납부자.적용시작학기ID`에는 `20261`이 저장되어 있어 코드상 FK(`feePayers.startSemesterId -> semesters.id`)가 끊겨 있다.

### 2.2 사용자 참조 의미와 컬럼명이 불일치

OperationDB 스키마의 다수 테이블은 `담당자ID`를 UserDB `users.email`에 연결한다. 실제 저장값의 의미는 ID가 아니라 Google 이메일이므로 이름과 데이터 의미가 일치하지 않는다.

### 2.3 실제 데이터에 잘못된 사용자 참조값 존재

현재 데이터에는 `admin@test.com`, `김은수`와 같이 UserDB `사용자.Google이메일`에 존재하지 않는 값이 있다. 이 값들은 FK를 만족하지 않으며 사용자 이름/임의 테스트 계정을 사용자 식별자로 사용하는 잘못된 상태다.

## 3. 설계 원칙

1. OperationDB에서 사용자를 참조할 때 source of truth는 항상 UserDB의 `사용자.Google이메일`이다.
2. 사용자 참조 컬럼명은 사용자의 업무 역할을 보존한다.
3. `담당자ID`처럼 실제 값의 타입과 다른 이름은 사용하지 않는다.
4. 이름, 학번, 임의 문자열을 사용자 FK로 저장하지 않는다.
5. 기존 잘못된 담당자 값은 삭제하고 현재 마이그레이션 기준 이메일 `mihy5012@mju.ac.kr`로 backfill한다.
6. 신규 데이터는 가능한 경우 요청을 실행한 인증 사용자의 실제 Google 이메일을 저장한다.
7. `처리자`, `등록자`, `승인자`, `확인자` 등 서로 다른 업무 역할은 모두 이메일 FK를 사용하되 컬럼명은 역할별로 구분한다.
8. 학기기준은 정규학기 `1학기`, `2학기`만 관리한다. 계절학기는 관리하지 않는다.

## 4. 사용자 참조 컬럼 명명 규칙

| 기존 의미 | 목표 컬럼명 | 내부 필드 권장명 | FK |
|---|---|---|---|
| 담당자 | `담당자이메일` | `managerEmail` | UserDB `사용자.Google이메일` |
| 처리자 | `처리자이메일` | `actorEmail` / `processorEmail` | UserDB `사용자.Google이메일` |
| 등록자 | `등록자이메일` | `createdByEmail` | UserDB `사용자.Google이메일` |
| 승인자 | `승인자이메일` | `approvedByEmail` | UserDB `사용자.Google이메일` |
| 확인자 | `확인자이메일` | `confirmedByEmail` | UserDB `사용자.Google이메일` |

`처리자이메일`을 `담당자이메일`로 합치지 않는다. 담당자는 업무 책임자이고 처리자는 특정 행위를 실행한 사용자이므로 의미가 다르다.

## 5. `담당자ID -> 담당자이메일` 변경 대상

현재 OperationDB 스키마에서 UserDB `users.email`을 참조하는 `managerId` 계열은 다음 테이블을 대상으로 한다.

- `회비납부자`
- `납부신청`
- `납부내역`
- `환불신청`
- `환불내역`
- `행사`
- `행사신청`
- `행사입금`
- `행사출석`
- `행사정산`
- `행사환불`
- `수입지출원장`
- `거래증빙`
- `감사대사`
- `결산보고서`

각 테이블은 물리 헤더 `담당자ID`를 `담당자이메일`로 변경하고, 코드 스키마 필드도 `managerId`에서 `managerEmail`로 변경한다.

`업무감사로그.처리자이메일`은 이미 의미가 올바르므로 물리 컬럼명은 유지한다. 다만 UserDB 이메일 FK 검증 대상에는 포함한다.

## 6. 기존 데이터 migration

### 6.1 담당자 데이터

기존 `담당자ID` 값 가운데 UserDB의 실제 `Google이메일`과 일치하지 않는 값은 보존하지 않는다.

현재 확인된 잘못된 값:

- `admin@test.com`
- `김은수`

이번 migration에서는 기존 업무 데이터의 담당자 값을 모두 `mihy5012@mju.ac.kr`로 backfill한다.

이미 유효한 UserDB 이메일이 저장된 행이 발견되면 원칙적으로 해당 값은 유지한다. 단, 이번 migration 대상 데이터에서 사용자가 명시적으로 일괄 보정을 승인한 잘못된 값은 `mihy5012@mju.ac.kr`로 교체한다.

### 6.2 audit actor 데이터

`업무감사로그.처리자이메일`은 과거 행위의 실행자 기록이므로 담당자 backfill 규칙을 적용하지 않는다. 존재하지 않는 이메일이 발견되면 자동으로 다른 사람으로 바꾸지 않고 integrity 오류로 보고한다. 감사 이력을 임의 사용자에게 귀속시키면 안 된다.

## 7. 학기기준 모델

학기 ID는 `{학년도}{학기번호}` 형식을 사용한다.

예:

- `20261`: 2026년 1학기
- `20262`: 2026년 2학기
- `20271`: 2027년 1학기
- `20272`: 2027년 2학기

`학기구분` 허용값은 다음 두 개뿐이다.

- `1학기`
- `2학기`

계절학기 값은 코드 validation과 시트 validation에서 제거한다.

### 7.1 초기 기준 데이터

현재 FK 복구에 반드시 필요한 `20261`을 포함해 2026년 정규학기 기준을 생성한다.

- `20261 / 2026 / 1학기`
- `20262 / 2026 / 2학기`

시작일/종료일은 임의로 추정하지 않는다. 기존 프로젝트 설정 또는 사용자가 승인한 실제 운영기간을 근거로 채운다. 근거가 없는 경우 nullable/빈 값이 허용되는 방향으로 스키마 검증을 조정하거나 migration 직전에 값을 확정한다.

활성여부는 기준 데이터의 사용 가능 여부를 의미하며, 최소 현재 운영 대상 학기는 활성으로 둔다.

## 8. 코드 변경 범위

### 8.1 스키마

`src/000_server/020_schema/operation_db_schema.gs`

- 각 대상 테이블 `managerId` -> `managerEmail`
- 물리 컬럼 `담당자ID` -> `담당자이메일`
- FK는 계속 UserDB `users.email` 참조
- semester `type` 허용 의미를 `1학기/2학기`로 제한

### 8.2 integrity

`src/000_server/020_schema/operation_db_integrity.gs`

- 사용자 FK 검사 시 변경된 `managerEmail`을 사용
- `업무감사로그.actorEmail`도 UserDB 사용자 FK 검사 대상으로 명시
- 잘못된 사용자 참조값을 테이블/행/컬럼 단위로 식별 가능하게 보고
- 학기 ID 중복 및 `회비납부자.startSemesterId` dangling FK 검증
- 학기구분이 `1학기/2학기` 이외이면 오류

### 8.3 서비스/DAO

스키마 key 변경의 영향을 받는 server 코드를 전수 검색한다.

변경 원칙:

- request payload에서 임의 `managerId`를 신뢰하지 않는다.
- 서버 context의 인증 이메일을 사용해야 하는 mutation은 `managerEmail`에 해당 이메일을 기록한다.
- 조회 DTO에서 필요한 경우 기존 프론트 호환 필드는 프론트 전수 작업까지 한시적으로 유지할 수 있으나 DB 저장 필드는 `managerEmail` 하나만 source of truth로 둔다.

프론트엔드 전수 변경은 별도 작업이므로 이번 브랜치에서 UI 구조 변경은 하지 않는다.

## 9. 실제 Google Sheet migration 순서

1. OperationDB 전체 백업 생성 또는 기존 최신 백업 유효성 확인
2. migration 전 관련 테이블 헤더/데이터 snapshot 확인
3. `학기기준`에 기준 데이터 추가
4. 대상 테이블 `담당자ID` 헤더를 `담당자이메일`로 변경
5. 기존 잘못된 담당자 값을 `mihy5012@mju.ac.kr`로 backfill
6. 사용자 이메일 컬럼에 text 형식과 필요한 validation 적용
7. 학기구분 validation을 `1학기/2학기`로 제한
8. 코드 변경 배포 전후 integrity 검사
9. dangling semester FK = 0 확인
10. invalid manager email FK = 0 확인
11. 변경 전후 행 수 및 PK 집합 동일 여부 확인

데이터 행을 삭제하는 migration은 수행하지 않는다.

## 10. 검증 기준

작업 완료 조건:

- `학기기준`에 현재 참조되는 `20261`이 존재한다.
- 2026년 정규학기 기준이 `20261`, `20262` 형식으로 존재한다.
- `학기구분`에 계절학기 값이 허용되지 않는다.
- 대상 테이블에 물리 컬럼 `담당자ID`가 남아 있지 않는다.
- 대상 테이블의 사용자 FK 물리 컬럼은 `담당자이메일`이다.
- 기존 잘못된 담당자 값 `admin@test.com`, `김은수`가 대상 담당자 컬럼에 남아 있지 않는다.
- migration 대상 기존 담당자 데이터는 `mihy5012@mju.ac.kr` 또는 다른 유효한 UserDB 이메일이다.
- OperationDB 사용자 FK dangling reference가 0건이다. 감사로그의 과거 invalid actor가 존재할 경우 해당 건은 별도 오류로 명시하고 임의 backfill하지 않는다.
- `회비납부자.startSemesterId` dangling FK가 0건이다.
- migration 전후 기존 업무 레코드의 PK와 행 수가 보존된다.
- 관련 테스트와 naming/integrity verifier가 통과한다.

## 11. 비범위

이번 작업에 포함하지 않는다.

- Accounting 프론트엔드 v2 정합화
- 전체 프론트엔드 전수 수정
- 업무감사로그 action/target taxonomy 재설계
- `납부폼_응답` raw source 구조 변경
- OperationDB 전체 물리 타입/validation 전수 정리
- 2027년 이후 학기 데이터 선생성
- UserDB 사용자 추가/삭제

이 항목들은 이후 별도 작업으로 진행한다.
