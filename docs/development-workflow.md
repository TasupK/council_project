# Apps Script 개발 작업 방식

이 문서는 학생회 통합 업무관리 프로젝트의 구조 설계, 구현, 검수 방식을 정의한다. 프로젝트의 현재 코드와 사용자가 합의한 규칙을 기준으로 한다.

## 1. 기본 원칙

- 기능을 추가하기 전에 기존 구조와 호출 흐름을 읽는다.
- 사용자가 작성한 주석은 명시적인 요청 없이 제거하지 않는다.
- 변경 범위 밖의 파일과 사용자 변경사항은 되돌리지 않는다.
- 서버와 클라이언트의 책임을 분리한다.
- 화면, 기능, 데이터 조회 범위를 같은 단위로 맞춘다.
- 미구현 기능의 UI를 유지해야 하면 실행 연결을 주석 처리하고 `TODO`로 이유를 남긴다.
- 람다식 대신 이름 있는 함수 또는 일반 `function` 표현식을 사용한다.
- 코드 순서는 실제 실행 흐름에 맞추고 단계 주석으로 구분한다.
- 구현 후 문법, DOM, include, API, 권한 경계를 검증한다.

## 2. 현재 디렉터리 규칙

```text
src/
├─ 000_server/
│  ├─ 001_init/          최초 권한 승인과 초기화
│  ├─ 010_core/          전역 설정, 응답, Sheet 공통 함수
│  ├─ 020_schema/        UserDB 스키마와 무결성 검증
│  ├─ 030_auth/          사용자, 역할, 권한 조회
│  ├─ 040_login/         세션, 로그인 컨텍스트, 캐시, 로그인 API
│  ├─ Code.js            doGet 라우터와 HTML 조립
│  └─ settings.gs        설정 페이지별 조회 API
├─ 100_common/           앱 전체 공통 View, 스타일, 클라이언트 JS
├─ 200_login/            로그인 페이지
├─ 250_main/             메인 페이지
└─ 300_settings/
   ├─ 300_home/          설정 홈
   ├─ 310_users/         사용자 관리
   ├─ 320_roles/         역할 관리
   ├─ 330_permissions/   업무 권한 설정
   └─ common/            설정 영역 전용 클라이언트 공통 코드
```

숫자 접두사는 Apps Script 편집기와 저장소에서 기능 순서를 직관적으로 표시한다. 하나의 독립 페이지는 진입 HTML, View, 클라이언트 JS를 같은 폴더에 둔다.

```text
Settings_Users.html
Settings_Users_View.html
settings_users_js.html
```

## 3. 서버와 클라이언트 경계

### 서버

`000_server`에 다음 책임을 둔다.

- Google Session 사용자 식별
- 로그인, 관리자, 업무 권한 검증
- Google Sheets와 Drive 접근
- 스키마와 PK/FK 무결성 검증
- 캐시와 잠금
- 페이지별 API 응답 생성

서버 기능은 기능 영역별 파일에 배치한다. 공개 API와 내부 함수의 이름만 바꾸는 불필요한 래퍼는 만들지 않는다.

### 클라이언트

HTML과 `*_js.html`에 다음 책임을 둔다.

- 화면 구조와 접근성 속성
- `google.script.run`을 통한 서버 API 호출
- 서버 응답 렌더링
- 검색, 필터, 표시 상태와 사용자 입력 처리
- 페이지 링크 생성

클라이언트에서 관리자 여부를 확인할 수 있지만 보안 경계로 사용하지 않는다. 데이터 반환 전 서버 API가 권한을 먼저 검사해야 한다.

### 템플릿

진입 HTML의 `<?= ... ?>`, `<?!= ... ?>`는 페이지 조립과 초기값 전달에만 사용한다. DB 조회와 업무 규칙을 템플릿에 넣지 않는다. `include()`로 삽입한 HTML 조각 내부의 템플릿 표현식은 다시 평가되지 않으므로, 동적 값은 진입 HTML에서 변수로 선언하거나 클라이언트에서 렌더링한다.

## 4. 페이지와 라우팅

화면 전환은 `doGet(e)`와 `?page=` 기반의 실제 페이지 라우팅을 사용한다.

```text
login
main
settings
settings_users
settings_roles
settings_permissions
```

- 독립 업무 화면을 하나의 HTML에 패널로 모두 넣지 않는다.
- 페이지 이동은 `<a target="_top">`를 기본으로 한다.
- Apps Script iframe에서 비동기 응답 이후 `window.top.location` 자동 이동에 의존하지 않는다.
- 보호 라우트는 HTML 반환 전에 서버에서 로그인을 검사한다.
- 설정 API는 데이터 조회 전에 서버에서 관리자 여부를 검사한다.
- 주소를 직접 입력해도 서버 API가 권한 없는 데이터를 반환하지 않아야 한다.

## 5. 공통 UI 기준

메인 화면의 헤더, 사이드바, 상태바를 앱 공통 레이아웃 기준으로 사용한다.

```text
100_common/
├─ App_Header.html
├─ App_Sidebar.html
├─ App_Styles.html
└─ app_shell_js.html
```

설정 영역의 공통 코드는 설정 API 호출과 오류 처리만 담당한다. 앱 전체에서 쓰는 레이아웃을 기능 폴더에 복제하지 않는다.

## 6. 로그인 컨텍스트 캐시

Google Session 이메일을 인증 기준으로 사용하고, 자체 브라우저 토큰을 인증 수단으로 만들지 않는다.

```text
Session 이메일 확인
→ ScriptCache 조회
→ 캐시 적중: 컨텍스트 반환
→ 캐시 누락: Lock 획득
→ 캐시 재확인
→ UserDB 조회와 무결성 검증
→ 10분 캐시 저장
```

- 캐시는 조회 최적화 수단이며 인증을 대체하지 않는다.
- 이메일은 SHA-256 기반 키로 변환한다.
- 캐시 오류가 로그인 전체를 중단시키지 않도록 로그를 남기고 DB 조회로 진행한다.
- 동시 캐시 생성은 `LockService`로 제한한다.
- 사용자 상태, 역할 배정, 역할 권한 저장 기능을 구현할 때 관련 로그인 캐시를 무효화한다.

## 7. 조회 API 설계

페이지는 필요한 데이터만 요청한다.

| 페이지 | API | 주요 반환 데이터 |
|---|---|---|
| 설정 홈 | `loadSettingsHomeData` | 앱, DB, 현재 사용자 |
| 사용자 관리 | `loadSettingsUsersData` | 사용자, 역할 |
| 역할 관리 | `loadSettingsRolesData` | 역할 |
| 업무 권한 | `loadSettingsPermissionsData` | 역할, 권한 트리, 역할별 권한 |

여러 페이지 데이터를 한 번에 반환하는 집계 API를 기본값으로 사용하지 않는다. 공통 응답은 별도 함수에서 만들고, 페이지별 데이터만 추가한다.

## 8. UserDB 규칙

- 시트 탭과 필드 이름은 `user_db_schema.gs`에서 정의한다.
- 조회 코드는 스키마의 필드 매핑을 사용한다.
- PK와 PK-FK 무결성 검증을 구분한다.
- 복합 관계는 불필요한 인조 ID보다 의미 있는 복합 PK를 우선한다.
- 로그인에서는 현재 사용자와 관련된 참조 무결성만 검사한다.
- 전체 DB 검사는 별도 API로 유지한다.

## 9. 구현 절차

1. 요청 범위와 현재 코드 흐름을 확인한다.
2. 관련 파일, 함수 정의, 호출부, 서버 API 존재 여부를 검색한다.
3. 페이지·기능·데이터 경계를 먼저 정한다.
4. 실패 조건 또는 검수 기준을 구현 전에 작성하고 실패를 확인한다.
5. 기존 명명, 주석, 코드 스타일에 맞춰 최소 변경한다.
6. 파일 수정 전 어떤 파일을 왜 바꾸는지 사용자에게 알린다.
7. 기능별로 구현하고 단계마다 문법과 참조를 검사한다.
8. 사용하지 않는 이전 구조는 새 구조가 검증된 후 제거한다.
9. 전체 검증 후 변경 내용과 남은 제한사항을 보고한다.
10. 사용자가 요청한 경우에만 `clasp push`, Git commit, push를 수행한다.

## 10. 검수 체크리스트

### 구조

- 모든 include 대상 파일이 존재한다.
- 이전 파일명과 이전 include 경로가 남지 않는다.
- 독립 페이지가 자체 View와 JS만 포함한다.
- 공통 레이아웃이 기능 폴더에 중복되지 않는다.

### JavaScript

- `.js`, `.gs`, `*_js.html` 스크립트의 문법 검사를 통과한다.
- 람다식 `=>`이 남지 않는다.
- 제거된 함수와 DOM ID 참조가 남지 않는다.
- 사용자가 작성한 주석이 보존되어 있다.

### HTML과 DOM

- 중복 `id`가 없다.
- JS가 정적으로 참조하는 DOM ID가 실제 View 또는 동적 HTML에 존재한다.
- 긴 줄은 읽을 수 있게 줄바꿈한다.
- 페이지 링크는 올바른 보호 라우트를 가리킨다.

### 서버와 보안

- 공개 API 함수가 실제로 구현되어 있다.
- 미구현 API의 활성 호출이 없다.
- 보호 API는 데이터 조회 전에 로그인과 권한을 검사한다.
- 캐시는 인증을 우회하지 않는다.
- 페이지별 API가 불필요한 전체 데이터를 반환하지 않는다.

### 완료

- `git diff --check`를 통과한다.
- 실제 Apps Script 배포 테스트를 하지 못했다면 명확히 보고한다.
- 로컬 변경과 Apps Script push 상태를 구분해 보고한다.

## 11. 현재 제한사항

- 사용자, 역할, 권한 저장 서버 함수는 아직 구현되지 않았다.
- Drive 연결 UI는 유지하지만 서버 연결 함수는 비활성 상태다.
- 메인 현황과 빠른 실행 데이터는 현재 정적 예시다.
- 현재 변경사항은 `clasp push` 전까지 Apps Script 프로젝트에 반영되지 않는다.
